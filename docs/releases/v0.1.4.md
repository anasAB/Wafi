## ⚠️ Deployment step required
This project has no CI auto-migration pipeline — migrations are applied
manually via the Supabase SQL editor. Before (or immediately after) this
client build goes live, paste
`supabase/migrations/072_register_device_rpc.sql` into the SQL editor for
project `eazyrdnvsiyaaccvjbhb` and run it. Without it, `register_device` does
not exist server-side and the RPC call this release adds will fail (falling
back to a temp code every time, not a regression from v0.1.3, but not the fix
either).

## Changes
- **Real fix for device self-registration** (v0.1.2 attempted this and had
  to be reverted in v0.1.3 — this replaces that attempt properly).
  `devices` INSERT is owner-only RLS (`055_identity_domain_rls.sql`), but
  `switch_active_operator()` (045) requires the `devices` row to already
  exist server-side before `active_role` can become `'owner'` — a circular
  dependency for any device without an already-registered code. New
  migration `072_register_device_rpc.sql` adds `register_device(p_device_id)`,
  a `SECURITY DEFINER` RPC mirroring `bootstrap_owner_identity()` (069) and
  `record_device_session_id()` (067): it creates the `devices` row directly,
  bypassing the owner-only RLS entirely, so it works for any authenticated
  shop member regardless of `active_role`. Safe because it only ever
  creates a row scoped to the caller's own shop (via `auth_shop_id()`) —
  exactly the boundary the owner-only RLS otherwise protects.
- **Fixed an independent bug found alongside this:** `device.store.ts`
  generated its own `uuidv4()` for `deviceId` while
  `useDeviceRegistration.ts`'s `registerDevice()` generated a *different*
  one for the actual `devices.id` row — the two never matched, so every
  later `switch_active_operator` lookup targeted a device that didn't
  exist. `registerDevice()` now returns the id it registered and the store
  adopts that value.
- Offline first-run temp-code fallback (`T-xxxx`) is unchanged.
