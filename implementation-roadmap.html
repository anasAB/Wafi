Executive Summary

Methodology, scoring model, and high-level findings
This roadmap was built by cross-referencing the competitor gap analysis (ConnectPOS) with our internal suggested features list, then validated against the existing codebase architecture. Features are ordered by strategic priority within effort tiers. Each feature is scored on four dimensions: Retention Impact (35% weight), Revenue Impact (35%), Operational Efficiency (20%), and Competitive Parity (10%) — these combine to produce the Platform Value Increase %. Value % is measured as improvement to a Monthly Active Business Score — a composite of three measurable KPIs: (a) average monthly revenue per active store, (b) 90-day user retention rate, and (c) feature parity gap closure vs. ConnectPOS benchmark. A feature rated 9/10 on all four dimensions represents approximately +18% to the composite score. Features compound — implementing Custom Reports before AI Assistant amplifies both.

Data Backup & Bulk Export

On-demand full backup, disaster recovery, and one-click Excel export for all business data
Low Effort High Impact +8% Platform Value
🚨 This should be the first feature shipped. IndexedDB data lives in the browser profile — a corrupted Chrome update, an OS reinstall, or an accidental "Clear site data" click = total, unrecoverable data loss. Every other feature in this roadmap is worthless without data safety. Before building anything else, build the escape hatch.

What It Is

Two complementary export paths: (1) Full Backup — serialize all Dexie tables to a single JSON file (download to local disk). The backup is importable for disaster recovery — one click restores all data. (2) Bulk Excel Export — uses the existing xlsx library already in the project to export all sales, customers, products, and expenses into separate sheets of one Excel file. Also: a scheduled backup reminder notification ("Last backup: 7 days ago — back up now").

Why It Matters

  • IndexedDB is not persistent by default — browsers can evict it under storage pressure
  • Business owners have no IT department — they need a simple "save everything" button
  • Regulatory compliance: many countries require businesses to keep financial records for 5–7 years
  • Excel export satisfies accountant/auditor requests without needing to share platform access
  • Backup restore enables switching devices or reinstalling OS without data loss

DB Changes

None — reads all existing tables. One new settings key:

settings: lastBackupAt, backupReminderDays

No schema changes needed. The backup format is a JSON object with one key per table name.

New Files

  • services/backupService.ts — serialize/deserialize all Dexie tables
  • "Backup & Export" tab in SettingsPage.tsx
  • Backup reminder notification trigger
  • Restore flow with row count verification

Export Formats

  • JSON backup — full restore capability, all tables
  • Excel export — separate sheets: Sales, Products, Customers, Expenses, Inventory, Providers
  • Uses existing xlsx package (already installed)
  • File name includes date: LedgerPro_Backup_2026-03-27.json

Implementation Steps

Build backupService.ts — exportAll() reads every Dexie table via db.table.toArray(), composes into a JSON object keyed by table name, triggers a browser download as .json.
Build restore flow — File picker accepts .json backup. Parse and validate structure (check required table keys, show row counts per table). Confirmation dialog. db.table.bulkPut() for each table. Show success/error per table.
Build Excel export — Using existing xlsx library: create workbook, add one sheet per entity type, format dates and currency values. Trigger download as .xlsx.
Add backup reminder notification — On app load, check settings.lastBackupAt. If more than N days (configurable, default 7), create a backup_reminder notification. Update lastBackupAt after every successful backup.
Add "Backup & Export" tab to Settings — Shows last backup date, backup button, restore button, Excel export button. Simple, prominent UI — should be impossible to miss.

Drag-and-drop report designer — any metric, any dimension, any chart type — the analytical foundation for all later features
Medium Effort High Impact +14% Platform Value
Why #5 and not #9? Every analytical feature that follows — demand forecasting, AI assistant, product velocity insights — produces better results when you can first verify your data is complete and clean using flexible custom reports. Custom Reports is the data validation layer. Build it before you build features that depend on data quality.

What It Is

A report designer where owners pick dimensions (product, category, date, customer, employee) and metrics (revenue, profit, quantity, margin %) from a panel, choose a chart type (bar, line, pie, table), apply filters, then save and name the report. Saved reports appear in a "My Reports" dashboard. All data comes from existing local DB entities.

Why It Matters

  • Every business has unique KPIs — fixed reports never satisfy everyone
  • Reduces requests for one-off analyses ("can you show me…?")
  • Neither ConnectPOS nor most SMB POS tools offer a true report builder
  • High perceived value — makes the platform feel enterprise-grade
  • Enables data validation before AI/forecasting features are built on top

  • Employee / Cashier

Available Metrics

  • Units Sold, Transaction Count
  • Gross Profit, Net Profit

  • Average Sale Value
  • Total Expenses

Historical Data Import

CSV import for past sales, customers, and products — make all analytics work from day one, not month six
Low–Med Effort High Impact +7% Platform Value
Deploy-time feature — highest value on day 1. This feature's value is front-loaded: it should be prioritized at platform deployment. Every day without historical import is a day where demand forecasting has no baseline, RFM segmentation shows every customer as "New", and the AI assistant has no data to analyze. Import history first, then the entire analytical layer becomes immediately useful.

What It Is

A CSV import wizard for three entity types: (1) Customers — name, phone, email, address, purchase history totals. (2) Products — SKU, name, category, purchase/sale price, current stock. (3) Sales history — date, product, quantity, price, customer reference. The wizard includes column mapping (handles varied column names from different systems), data validation with a preview table before committing, and duplicate detection.

Why It Matters

  • Businesses switching from Excel/paper have 1–5 years of history that must not be lost
  • Demand forecasting produces garbage predictions without historical sales data
  • RFM segmentation requires purchase history — without import, all customers start as "New"
  • The AI assistant's data context is built from historical records — more history = better answers
  • Duplicate detection prevents double-entry of existing products/customers

DB Changes

None — imports into existing tables. One new audit log entry type:

auditLogs: new action type bulk_import

All imported records use the standard entity schema. Historical sales are tagged with source: 'import' for traceability.

New Files

  • Extended components/import/ImportDialog.tsx (already exists)
  • services/historicalImportService.ts
  • Column mapper UI (drag CSV header → entity field)
  • Validation + preview step before commit
  • Import progress bar for large files

Duplicate Detection

  • Products: match on SKU (exact) or name (fuzzy)
  • Customers: match on phone number or email
  • Sales history: match on date + product + customer combo
  • User chooses: Skip / Update / Create new for each duplicate

Implementation Steps

Extend ImportDialog.tsx — Add entity type selector: Customers / Products / Sales History. Each type has its own column mapping template and validation rules.
Build column mapper UI — Parse CSV headers, show as chips. User drags each CSV header to match an entity field. "Auto-detect" button tries to match by common column names (Name, Phone, SKU, Date, etc.).
Validation & preview — After mapping, parse all rows and show: total rows, valid rows, invalid rows (with error reason), and a 10-row preview table. Block import if >20% of rows are invalid.
Duplicate detection — For each entity type, run duplicate checks against existing DB records. Present duplicates as a separate resolution step before final import.
Batch insert with progress — Use Dexie bulkPut() in chunks of 500 rows. Show progress bar. On completion: show import summary (X customers added, Y products updated, Z sales imported). Log to audit trail.

Each product gets three additional price fields beyond the existing salePrice: wholesalePrice, vipPrice, bulkPrice. A utility function resolvePrice(product, tier) is the single source of truth — it returns the correct price for a given customer tier, falling back to salePrice if the tier-specific price is not set. The Wholesale POS auto-applies the customer's tier; the owner can override; employees see the price as read-only.

  • Profit tracking still works — costPrice stays constant, only unitPrice changes by tier

Multi-Device Sync (Supabase)

Real-time shared database across 2 PCs in the store — wholesale accounts, prices, and stock always in sync
High Effort High Impact +20% Platform Value
⚠️ Architectural Note — W8 Should Be a Prerequisite, Not the Last Step
This feature is listed last because it's the most complex, but it is architecturally the most critical for a 2-device store. Running W1–W7 without sync means: wholesale customer debts updated on PC1 are invisible on PC2, stock deducted on PC1 is not reflected on PC2, and price tier changes don't propagate. If you have two active devices in your store today, W8 should be implemented before or alongside W4 (Credit & Debt) and W5 (Wholesale POS). The sequencing here assumes single-device testing of the wholesale module during development — switch to multi-device mode only after W8 is deployed.

What It Is

The existing app uses Supabase (already a dependency) as a cloud backend for sync and backup. For wholesale specifically, two PCs in the same store must see the same customer debts, stock levels, and price tiers in real-time. Supabase provides a Postgres database with real-time subscriptions — the app writes to local IndexedDB first (offline-first) and syncs to Supabase on connectivity. Supabase broadcasts changes to other connected clients via WebSocket.

Why It Matters

  • Without sync: PC1 sells 10 cartons → PC2 still shows old stock → oversell
  • Customer debt changes on PC1 must be visible on PC2 before accepting new orders
  • Price tier updates (owner on PC2) must apply immediately on employee's PC1
  • Supabase is already installed — this is configuration + schema work, not a new dependency

What Needs Sync

  • New product_units table
  • Customer new fields (businessName, taxNumber, creditLimit, priceTier)
  • Product price tier fields
  • Sales + credit ledger entries (already syncs)
  • Real-time stock after each wholesale sale

Supabase Schema Work

  • Create product_units table in Supabase dashboard
  • ALTER TABLE customers ADD COLUMN for 4 new fields
  • ALTER TABLE products ADD COLUMN for 4 price tier fields
  • Enable Realtime on products, customers, credit_ledger_entries

App-Side Work

  • Add syncUpsertProductUnit() to sync service
  • Extend customerService.ts create/update to include new fields
  • Subscribe to Supabase Realtime changes → update local Dexie DB
  • Conflict resolution: last-write-wins (simple, sufficient for 2-device store)

Implementation Steps

Configure Supabase credentials — set up Supabase project, get VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY in .env.
